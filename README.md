# Лабораторна робота №2: Від C до Assembly та машинного коду

## 1. Мета лабораторної роботи
Простежити шлях перетворення програми від вихідного коду мовою C до машинних інструкцій, які безпосередньо виконує процесор (`C source code → Compiler → Assembly → Assembler → Machine code → CPU`), навчитися читати базовий код Assembly у синтаксисі Intel та встановлювати відповідність між конструкціями C (арифметика, розгалуження `if/else`, цикли, виклики функцій) і машинними командами.

**Головне питання лабораторної роботи:** *Що насправді виконує процесор замість написаного нами C-коду?*

---

## 2. Середовище виконання
* **Середовище:** GitHub Codespaces (Ubuntu Linux, архітектура `x86_64`)
* **Компілятор:** GCC (`gcc -Wall -Wextra -O0 -S -masm=intel`)
* **Дизасемблер:** GNU Binutils `objdump` (`objdump -d -M intel`)

## 3. Короткі результати експериментів

### Підготовка першої програми та Завдання 1 (`arithmetic.c`)
* **Прогноз логіки CPU для `int result = a + b;`:** Процесор зчитує значення `5` з комірки пам'яті (стеку), що відповідає змінній `a`, у свій внутрішній регістр, додає до нього значення `7` з комірки пам'яті змінної `b` за допомогою арифметико-логічного пристрою (ALU), а отриманий результат (`12`) записує назад у комірку пам'яті, виділену під змінну `result`.
* **Відповіді за результатами аналізу `arithmetic.s` / `arithmetic_intel.s`:**
  1. **Чи кожному рядку C відповідає рівно одна Assembly-інструкція?** Ні. Один рядок на C розкладається на кілька елементарних інструкцій пересилання даних між пам'яттю (стеком) та регістрами, обчислення і підготовки аргументів функцій.
  2. **Чи є в Assembly змінні з назвами `a`, `b`, `result`?** Ні. Імена локальних змінних існують лише на етапі компіляції; у машинному коді вони замінюються на адреси зі зміщенням відносно вказівника базового кадру стеку `rbp` (наприклад, `DWORD PTR -12[rbp]`, `DWORD PTR -8[rbp]`, `DWORD PTR -4[rbp]`).
  3. **Скільки Assembly-інструкцій приблизно відповідає тілу `main()`?** Близько **15–18 інструкцій** (разом із прологом кадру стеку, ініціалізацією змінних, викликом `printf` та епілогом `ret`).
  4. **Чи присутня операція додавання?** Так, у синтаксисі Intel вона представлена інструкцією `add eax, edx`.

### Завдання 2. Арифметичні операції (`operations.c`)
При послідовній заміні виразу у функції `calculate(int a, int b)` зафіксовано зміну арифметичної інструкції в Assembly (при рівні оптимізації `-O0` аргументи `a` та `b` передаються через регістри `edi` і `esi`, зберігаються у стек `[rbp-4]` та `[rbp-8]`, після чого завантажуються в `eax` та `edx`):

| Операція в C | Основна Assembly-інструкція (Intel) | Пояснення дії |
| :--- | :--- | :--- |
| `a + b` | `add eax, edx` | Додавання значення регістра `edx` до `eax` (`eax = eax + edx`) |
| `a - b` | `sub eax, edx` | Віднімання значення регістра `edx` від `eax` (`eax = eax - edx`) |
| `a * b` | `imul eax, edx` | Знакове множення `eax` на `edx` (`eax = eax * edx`) |

**Пояснення:** Після зміни однієї арифметичної операції в C у згенерованому Assembly змінюється лише сама мнемоніка обчислювальної команди (`add` → `sub` → `imul`). Інструкції завантаження аргументів зі стеку в регістри та повернення результату через регістр `eax` залишаються повністю незмінними.

### Завдання 3. Конструкція `if / else` на машинному рівні (`condition.c`)

Фрагмент отриманого Assembly для `max_value`:
```assembly
max_value:
    push    rbp
    mov     rbp, rsp
    mov     DWORD PTR -4[rbp], edi
    mov     DWORD PTR -8[rbp], esi
    mov     eax, DWORD PTR -4[rbp]
    cmp     eax, DWORD PTR -8[rbp]
    jle     .L2
    mov     eax, DWORD PTR -4[rbp]
    jmp     .L3
.L2:
    mov     eax, DWORD PTR -8[rbp]
.L3:
    pop     rbp
    ret
```

**Таблиця відповідності:**

| Конструкція в C | Інструкції в Assembly |
| :--- | :--- |
| `if (a > b)` | `cmp eax, DWORD PTR -8[rbp]` |
| *(перехід, якщо `a <= b`)* | `jle .L2` |
| `return a` | `mov eax, DWORD PTR -4[rbp]` |
| *(вихід із функції)* | `jmp .L3` |
| `else` | `.L2:` |
| `return b` | `mov eax, DWORD PTR -8[rbp]` |

**Контрольне питання: Чи існує машинна інструкція `IF`?**  
Ні, окремої інструкції `IF` у системі команд процесора не існує. CPU реалізує розгалуження у два кроки:
1. Інструкція **`cmp`** (compare) виконує приховане віднімання `a - b` (не змінюючи самі операнди) та встановлює прапорці стану в регістрі `RFLAGS` (зокрема прапорець нуля `ZF`, знаку `SF` та переповнення `OF`).
2. Інструкція умовного переходу **`jle`** (*Jump if Less or Equal*) перевіряє ці прапорці. Компілятор інвертує умову `a > b`: якщо `a <= b`, процесор виконує стрибок на мітку `.L2` (гілка `else`). Якщо умова стрибка хибна (`a > b`), процесор продовжує лінійне виконання наступної інструкції (гілка `if`), а в кінці безумовним стрибком `jmp .L3` обходить код гілки `else`.

### Завдання 4. Цикл на машинному рівні (`loop.c`)

Фрагмент отриманого Assembly для `sum_to`:
```assembly
    mov     DWORD PTR -4[rbp], 0      # int sum = 0 (ініціалізація суми)
    mov     DWORD PTR -8[rbp], 1      # int i = 1   (ініціалізація лічильника)
    jmp     .L2                       # перехід до перевірки умови
.L3:
    mov     eax, DWORD PTR -8[rbp]    # тіло циклу: завантажити i
    add     DWORD PTR -4[rbp], eax    # sum += i
    add     DWORD PTR -8[rbp], 1      # інкремент: i++
.L2:
    mov     eax, DWORD PTR -8[rbp]    # умова: завантажити i
    cmp     eax, DWORD PTR -20[rbp]   # порівняти i з n
    jle     .L3                       # якщо i <= n, стрибнути назад на .L3
```

**Відповіді на питання:**
1. **Яка інструкція виконує порівняння?** `cmp eax, DWORD PTR -20[rbp]` (порівнює лічильник `i` з межею `n`).
2. **Яка інструкція реалізує перехід?** Безумовний перехід `jmp .L2` на початку для першої перевірки умови та умовний перехід `jle .L3` наприкінці кожної ітерації.
3. **Чи існує в отриманому Assembly поняття `for`?** Ні, у машинному коді немає високорівневих циклів `for` чи `while` — є лише лінійні блоки інструкцій, мітки (`.L2`, `.L3`) та інструкції стрибків.
4. **Як CPU визначає, що цикл потрібно повторити?** Після збільшення лічильника (`add ..., 1`) інструкція `cmp` оновлює прапорці процесора, а умовний перехід `jle .L3` перевіряє, чи виконується умова `i <= n`. Поки вона істинна, інструкція `jle` перезаписує вказівник інструкцій (`RIP`) адресою мітки `.L3`, повертаючи виконання на початок тіла циклу.

### Завдання 5. Виклик функції (`operations.c`)
1. **Де знаходиться виклик `calculate`?** У тілі функції `main:` інструкцією `call calculate` (після завантаження аргументів `mov esi, 20` та `mov edi, 10`).
2. **Де починається код `calculate`?** З мітки `calculate:` та прологу стекового кадру (`push rbp`, `mov rbp, rsp`).
3. **Де функція завершується?** Після запису результату у регістр `eax` та відновлення покажчика базового кадру стеку (`pop rbp`).
4. **Де знаходиться `ret`?** У самому кінці блоку функції `calculate:` одразу після `pop rbp`.
5. **Який регістр містить результат функції перед поверненням?** Регістр **`eax`** (згідно зі стандартом виклику функцій System V AMD64 ABI).

**Питання: Чому після `call` CPU повинен мати спосіб визначити, куди повернутися?**  
Оскільки одну й ту саму функцію (`calculate`) можна викликати з різних місць програми, всередині самої функції не може бути зашитої адреси повернення. Тому інструкція `call` перед стрибком на функцію автоматично зберігає у стек адресу наступної після `call` інструкції (return address), а інструкція `ret` витягує цю адресу зі стеку назад у лічильник команд `RIP`.

### Завдання 6 та 7. Реальний machine code (`objdump -d -M intel operations`)

Приклад дизасемблювання функції `<calculate>` з виконуваного файлу:

| Address | Machine-code bytes | Assembly |
| :--- | :--- | :--- |
| `0x1129` | `55` | `push rbp` |
| `0x1136` | `8b 55 fc` | `mov edx, DWORD PTR [rbp-0x4]` |
| `0x113c` | `01 d0` | `add eax, edx` |
| `0x113f` | `c3` | `ret` |

**Відповіді на питання:**
1. **Що насправді зберігається у виконуваному файлі?** Виключно байти машинного коду (**machine code**, наприклад `55`, `01 d0`, `c3`).
2. **Навіщо тоді `objdump` показує Assembly?** Утиліта `objdump` виконує зворотне перетворення (дизасемблювання), розшифровуючи двійкові коди операцій (opcodes) та операнди у зрозумілі людині текстові мнемоніки Assembly.
3. **Чи всі машинні інструкції `x86-64` мають однакову кількість байтів?** Ні, архітектура `x86-64` (CISC) використовує інструкції змінної довжини — у наведеній таблиці вони займають від 1 байта (`55`, `c3`) до 3 байтів (`8b 55 fc`).
4. **Чому людині зручніше аналізувати Assembly, ніж байти machine code?** Текстові мнемоніки (`add`, `mov`, `ret`) та назви регістрів (`eax`, `edx`) одразу передають зміст операції, тоді як у машинному коді біти коду операції, напрямку пересилання та номерів регістрів упаковані всередину окремих байтів (наприклад, `01 d0`).

### Завдання 8 та 9. Експеримент з оптимізацією (`-O0` проти `-O2`, `optimize.c`)
* **Прогноз для `answer()` (`return 10 + 20;`):** **Варіант B** — оптимізуючий компілятор обчислить `10 + 20` під час компіляції і одразу поверне константу `30`.
* **Фактичне порівняння `optimize_O0.s` та `optimize_O2.s`:**
  * При **`-O0`**: створюються повноцінні функції `answer` та `main`, налаштовується стек (`push rbp`), виконується `call answer`, а всередині `answer` повертається `mov eax, 30` (складання констант GCC виконує навіть на `-O0`, але зберігає сам виклик функції).
  * При **`-O2`**: у `main` повністю зникає виклик `call answer` (**function inlining**) і робота зі стеком — уся програма скорочується до двох інструкцій:
    ```assembly
    main:
        mov     eax, 30
        ret
    ```
  * У файлі **`operations_O2.s`** компілятор також застосував *inlining* та *constant folding* для `calculate(10, 20)`, одразу підставивши число `30` як аргумент для `printf`.

**Чому компілятор має право замінити `10 + 20` готовим значенням `30`?**  
Згідно зі стандартом мови C діє правило *«as-if»*: компілятор має право будь-як трансформувати, спрощувати або видаляти код під час оптимізації, якщо спостережувана зовнішня поведінка програми (вивід, побічні ефекти, результат обчислень) залишається ідентичною.

### Фінальне завдання — аналіз програми `analyze.c`

У файлі `analyze.c` реалізовано функцію `process_values(int start, int limit)`, яка поєднує розгалуження `if (start < limit)`, цикл `for`, арифметичне додавання (`total += 2`) та віднімання (`total = start - limit`).

**Три приклади ланцюжка `C construct → Assembly → Machine-code bytes` (з виводу `objdump -d -M intel analyze`):**

1. **Умова `if (start < limit)`:**
   * **C:** `if (start < limit)`
   * **Assembly:** `cmp eax, DWORD PTR [rbp-0x18]` та `jge 117b <process_values+0x42>`
   * **Machine code:** `3b 45 e8` та `7d 20`

2. **Арифметична операція у тілі циклу `total += 2;`:**
   * **C:** `total += 2;`
   * **Assembly:** `add DWORD PTR [rbp-0x4], 0x2`
   * **Machine code:** `83 45 fc 02`

3. **Повернення результату `return total;`:**
   * **C:** `return total;`
   * **Assembly:** `mov eax, DWORD PTR [rbp-0x4]` та `ret`
   * **Machine code:** `8b 45 fc` та `c3`

## 4. Відповіді на контрольні питання

1. **Що таке ISA?** *Instruction Set Architecture* — архітектура набору інструкцій процесора, яка визначає підтримувані машинні команди, набір регістрів, типи даних та правила роботи з пам'яттю.
2. **Чому CPU не може безпосередньо виконувати C-код?** Апаратні схеми процесора працюють лише з електричними сигналами, закодованими як бінарні машинні інструкції конкретного формату, а не з текстом високого рівня.
3. **У чому різниця між Assembly та machine code?** *Machine code* — це числові байти інструкцій, які безпосередньо виконує CPU. *Assembly* — це символьне (текстове) представлення тих самих інструкцій за допомогою мнемонік (`mov`, `add`, `jmp`), зрозуміле людині.
4. **Що робить параметр GCC `-S`?** Зупиняє процес компіляції після генерації коду мовою Assembly, зберігаючи його у текстовий файл `.s` без перетворення в об'єктний чи виконуваний файл.
5. **Навіщо ми використовували `-O0`?** Щоб вимкнути оптимізації компілятора і побачити прямий, незмінений переклад кожної конструкції C у машинні інструкції.
6. **Що таке operand?** Це аргумент машинної інструкції — дані або місце їх зберігання (регістр, адреса в пам'яті або константа), над якими виконується операція.
7. **Для чого використовується `mov`?** Для копіювання (пересилання) даних між регістрами процесора та комірками оперативної пам'яті або запису констант у регістр/пам'ять.
8. **Яку роль виконує `cmp`?** Порівнює два операнди шляхом їх віднімання та оновлює прапорці стану процесора (`RFLAGS`), не змінюючи значень самих операндів.
9. **Як на машинному рівні реалізується `if`?** За допомогою комбінації інструкції порівняння (`cmp`) та інструкції умовного переходу (`jle`, `jge`, `je`, `jne`), яка передає керування на відповідну мітку коду.
10. **Як реалізується цикл?** Через ініціалізацію лічильника, мітку початку циклу, інструкцію зміни лічильника, порівняння з умовою виходу (`cmp`) та умовний стрибок (`jle`, `jl` тощо) назад на початок тіла циклу.
11. **Для чого потрібна інструкція `call`?** Для виклику підпрограми (функції): вона зберігає адресу наступної інструкції у стек (як адресу повернення) і передає керування на першу інструкцію функції.
12. **Для чого потрібна `ret`?** Для завершення роботи функції: вилучає зі стеку збережену адресу повернення і повертає виконання програми в точку виклику.
13. **Чому одному рядку C не обов’язково відповідає одна машинна інструкція?** Бо одна конструкція C може містити кілька елементарних дій (завантаження операндів з пам'яті в регістри, обчислення, запис результату назад у пам'ять).
14. **Що показує `objdump -d`?** Дизасемблює секції з виконуваним кодом бінарного файлу, виводячи адреси інструкцій, їхні реальні байти машинного коду та відповідні інструкції Assembly.
15. **Чому Assembly, отриманий з `-O0` та `-O2`, може суттєво відрізнятися?** На рівні `-O2` компілятор оптимізує код за швидкістю: тримає змінні в регістрах замість стеку, вбудовує короткі функції (*inlining*), заздалегідь обчислює константи (*constant folding*) та перевпорядковує інструкції.
16. **Чи може компілятор повністю видалити частину написаного програмістом C-коду? За яких умов?** Так, якщо цей код є недосяжним (*dead code*, наприклад `if (0)`), обчислює результат, який ніде далі не використовується, і не має побічних ефектів (вводу/виводу чи роботи з `volatile`-пам'яттю).

## 5. Висновок
У ході лабораторної роботи було експериментально простежено перетворення вихідного коду мовою C у текстовий Assembly (`-S`) та реальний машинний код (`objdump -d`). Встановлено, що високорівневі абстракції мови C — змінні, умови `if/else`, цикли `for` та виклики функцій — на рівні процесора `x86-64` реалізуються за допомогою операцій над регістрами й стеком, прапорців стану та умовних або безумовних стрибків за адресами інструкцій. Також на практиці підтверджено, що рівень оптимізації (`-O2`) кардинально змінює структуру згенерованого машинного коду зі збереженням логічного результату програми.
